# Исследование SPI-mapping для Black Pill и Blue Pill

Статус: исследование завершено. На его основе первым реализован и проверен
срез для STM32F401; F1/Blue Pill пока не изменялись.

## Цель этапа

Зафиксировать физически доступные варианты SPI для двух целевых связок:

- Black Pill — STM32F401;
- Blue Pill — STM32F103C8T6.

Это нужно сделать до изменения общей модели `SpiConfig` и GUI: текущий интерфейс позволяет независимо выбрать шину, SCK, MISO и MOSI, но пока не знает, какие сочетания действительно поддерживаются выбранным MCU.

## Источники и версии

Для F4 текущая генерация ориентируется на `stm32f4xx-hal 0.23.0` с feature `stm32f401`. В исходниках HAL feature `gpio-f401` включает периферии `spi3` и `spi4`, но не `spi5`.

Для Blue Pill эталонный проект использует `stm32f1xx-hal 0.11.0` с feature `stm32f103`. Документация HAL для SPI описывает F1-specific remap и конструктор SPI с типизированным tuple пинов:

- [stm32f1xx-hal 0.11.0: SPI](https://docs.rs/stm32f1xx-hal/0.11.0/stm32f1xx_hal/spi/index.html);
- [stm32f1xx-hal 0.11.0: `Spi::new`](https://docs.rs/stm32f1xx-hal/0.11.0/stm32f1xx_hal/spi/struct.Spi.html);
- [stm32f4xx-hal 0.23.0: SPI](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/spi/index.html);
- [stm32f4xx-hal 0.23.0: feature flags](https://docs.rs/crate/stm32f4xx-hal/0.23.0/features).

## Решение для текущего инкремента

Remap SPI1 STM32F1 исследован, но в реализацию не включается. Первый вариант
модели использует только готовые mapping без AFIO/remap-настроек.

Сначала проверяется только Black Pill/F401. Пользователь выбирает полную
совместимую тройку SCK/MISO/MOSI, а не произвольные GPIO. После успешной
проверки этого подхода та же capability-модель будет расширена для Blue Pill.

## Blue Pill: STM32F103C8T6

Для первой реализации поддерживаем только SPI1 и SPI2. Хотя общая F1-документация также показывает SPI3, его не следует добавлять в capability целевого STM32F103C8T6 без отдельной проверки конкретного PAC и корпуса.

### SPI1

SPI1 имеет две аппаратные конфигурации:

| Вариант | SCK | MISO | MOSI | AFIO remap |
|---|---|---|---|---|
| Default | PA5 | PA6 | PA7 | 0 |
| Remapped | PB3 | PB4 | PB5 | 1 |

Это именно групповые варианты SPI1: при выборе remap нужно использовать всю группу PB3/PB4/PB5 и включить соответствующий remap в AFIO. Нельзя считать remap только свойством отдельного пина.

Для первого TCP/W5500 fixture выбирается default-вариант PA5/PA6/PA7. Он совпадает с эталонным Blue Pill проектом и не требует дополнительного управления remap.

### SPI2

SPI2 имеет один стандартный вариант:

| Вариант | SCK | MISO | MOSI |
|---|---|---|---|
| Default | PB13 | PB14 | PB15 |

Для обычного full-duplex SPI tuple HAL ожидает `(SCK, MISO, MOSI)` в указанном порядке. Линии MISO и MOSI могут быть исключены для read-only/write-only сценариев через `None`/`NoMiso`/`NoMosi`, но для W5500 нужны все три линии.

### Ограничения и аппаратные замечания

- PB3/PB4 относятся к JTAG-пинам. Remapped SPI1 может потребовать настройки SWJ/JTAG так, чтобы сохранить SWD для прошивки и отладки; это отдельная F1-специфичная часть генератора.
- PA13/PA14 нужно оставить в полном pinout как SWD-пины. Это не SPI-пины, но их наличие важно для выбранного способа прошивки и отладки.
- В Blue Pill нельзя показывать SPI3 только потому, что он есть в общей странице документации F1: capability должна зависеть от конкретного MCU, а не только от семейства.
- Для W5500 на текущем этапе достаточно SPI1 default. SPI2 должен быть доступен как корректная опция для самостоятельных конфигураций, но не нужен в fixture-проекте.

Официальная таблица F1 и пример конструктора подтверждают default/remap для SPI1, PB13/PB14/PB15 для SPI2 и optional-пины SPI: [документация `stm32f1xx-hal::spi`](https://docs.rs/stm32f1xx-hal/0.11.0/stm32f1xx_hal/spi/index.html).

## Black Pill: STM32F401

Ниже перечислены пины, которые `stm32f4xx-hal 0.23.0` объявляет для feature `gpio-f401`. Для F4 remap-регистр F1 не используется: каждый сигнал выбирается из списка GPIO-пинов с подходящей alternate function, обычно AF5.

### SPI1

| Сигнал | Доступные пины |
|---|---|
| SCK | PA5, PB3 |
| MISO | PA6, PB4 |
| MOSI | PA7, PB5 |

### SPI2

| Сигнал | Доступные пины |
|---|---|
| SCK | PB10, PB13, PD3 |
| MISO | PB14, PC2 |
| MOSI | PB15, PC3 |

### SPI3

| Сигнал | Доступные пины |
|---|---|
| SCK | PB3, PC10 |
| MISO | PB4, PC11 |
| MOSI | PB5, PC12, PD6 |

### SPI4

| Сигнал | Доступные пины |
|---|---|
| SCK | PE2, PE12 |
| MISO | PE5, PE13 |
| MOSI | PE6, PE14 |

### SPI4 и SPI5

SPI4 имеет mapping через PE2/PE5/PE6 или PE12/PE13/PE14 на уровне MCU
capability. В текущем Black Pill pinout эти PE-пины не выведены, поэтому
SPI4 не показывается пользователю этой платы. SPI5 не является поддерживаемой
peripheral feature для F401: в HAL feature `stm32f401` включены `spi3` и
`spi4`, но не `spi5`, а PAC STM32F401 не содержит SPI5. В реализации F401
на уровне чипа доступны SPI1, SPI2, SPI3 и SPI4.

Списки F4 сформированы по таблицам alternate-function в исходнике HAL: [SPI1](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/gpio/alt/spi1/index.html), [SPI2](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/gpio/alt/spi2/index.html), [SPI3](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/gpio/alt/spi3/index.html), [SPI4](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/gpio/alt/spi4/index.html), [SPI5](https://docs.rs/stm32f4xx-hal/0.23.0/stm32f4xx_hal/gpio/alt/spi5/index.html). Наличие страницы SPI5 в общей документации не означает, что она доступна при feature `stm32f401`.

Для STM32F401 практический вывод такой: capability должна содержать SPI1–SPI4 и списки пинов по каждому сигналу, а не просто enum всех SPI, встречающихся в HAL для других F4-чипов.

## Что это означает для общей модели

### 1. Нужна capability-матрица, а не проверка только на дубликаты

Текущая проверка `SpiConfig` защищает от одинаковых SCK/MISO/MOSI, но не от физически невозможной пары «шина + пин». Минимальная будущая модель должна уметь ответить:

```text
is_spi_pin_supported(mcu, bus, role, pin) -> bool
```

где `role` — `Sck`, `Miso` или `Mosi`. Для F1 дополнительно нужен вариант SPI1 remap как свойство всей конфигурации SPI, а не отдельного GPIO.

### 2. Одного множества пинов на роль недостаточно для F1 remap

Для STM32F4 достаточно хранить допустимые пины каждой роли для конкретной шины: AF задаётся на GPIO-пинах.

Для STM32F1 лучше описывать SPI mapping группами:

```text
SPI1:
  - remap: false, SCK=PA5, MISO=PA6, MOSI=PA7
  - remap: true,  SCK=PB3, MISO=PB4, MOSI=PB5
SPI2:
  - remap: false, SCK=PB13, MISO=PB14, MOSI=PB15
```

Так GUI сможет предложить пользователю только целые аппаратные варианты, а генератор получит однозначную информацию о необходимости `afio.mapr`.

### 3. Optional MISO/MOSI остаются общим поведением

HAL обоих семейств поддерживает отсутствие части линий через `Option`/`NoMiso`/`NoMosi`. Это не повод заводить отдельную Blue Pill-логику в Config или GUI. Проверка должна применять mapping только к реально выбранным линиям, а генератор — использовать F1/F4-specific синтаксис создания SPI.

## Последствия для GUI

На этапе 1 изменений GUI не требуется. После добавления capability-модели ожидается небольшой рефакторинг существующей SPI-формы:

1. форма получает допустимые mappings через `TargetMcu`, а не строит список пинов только из `all_pins()`;
2. после выбора шины показываются только совместимые mapping-группы или совместимые пины;
3. при Blue Pill для SPI1 должен отображаться выбор default/remap, при этом fixture по умолчанию использует default;
4. занятые GPIO по-прежнему фильтруются общей логикой Config;
5. страницы W5500 и GPIO должны продолжить использовать общие `ChosenPin`/`ChosenSpiBus` и не получать условных проверок на Blue Pill.

Таким образом, теоретически GUI-изменение должно затронуть в основном источник данных SPI-формы и пересборку списков после выбора шины/mapping. Архитектуру страниц, W5500-формы и отображение выбранной платы менять не требуется.

## Решение, принимаемое перед этапом 2

Для будущего расширения Blue Pill следует сохранить общую capability-абстракцию:

- Black Pill: STM32F401, только SPI1–SPI3, поскольку PE-пины SPI4 не входят
  в текущий pinout платы;
- Blue Pill: STM32F103C8T6, SPI1 default и SPI2 default; remap не включать;
- Config валидирует mapping до добавления SPI;
- GUI использует ту же capability для фильтрации выбора;
- F1 remap хранится как часть выбранного SPI mapping и позже передаётся в F1-specific шаблон.

Это не меняет поведение TCP/W5500 и не требует менять minijinja на данном этапе.
